# Приватний пілот ШІ у Telegram

У приватному чаті власника **/usage** показує залишок спільного з вебчатом ліміту за останню годину, локальний бюджет ШІ, витрати й резерви, останні отримані ліміти OpenAI та квоти Cloudflare. Релей читає лічильник ERP та стан шлюзу на вимогу. За недоступності джерела команда показує доступні розділи. Звіт проходить окремо від запитань і не витрачає дозволу. ERP допускає до 100 запитань за останні 60 хв для обох каналів разом. Після відповіді можна одразу надіслати наступне запитання. Змішане запитання враховується один раз. Для прив’язки задайте на сайті `vector_telegram_quota_user` з іменем користувача ERP (тут `Administrator`). Права на дані визначає обліковий запис Telegram ERP Reader.

Після прийняття запитання в приватному чаті власника бот показує «друкує…».
Кнопки під повідомленням мають такі самі короткі назви, як у вебпомічнику. Коли власник натискає тему, бот одразу публікує повне запитання окремим повідомленням, а під ним показує «🤖 Готую відповідь…» на час обробки.
Worker поновлює індикатор після отримання запитання й далі приблизно кожні півтори секунди, поки запит чекає на обробку,
поки релей готує відповідь і поки відповідь у черзі на доставку. Worker завершує поточне оновлення індикатора й надсилає відповідь окремим повідомленням. Telegram прибирає «друкує…», щойно відповідь з’являється в чаті. Якщо бот устиг показати проміжне повідомлення про обробку, після відповіді він його прибирає. Оновлення
припиняються після доставки. Якщо Telegram обмежує частоту запитів,
бот витримує вказану сервісом паузу. За оновлення відповідає прив’язка
`REPLY_TYPING` у конфігурації Worker.

У приватному Telegram-чаті власника і в [помічнику робочого простору](ai-chat.uk.md)
можна поєднати запитання про залишки й умови гарантії. У Telegram кожен запит
самостійний. У робочому просторі доступні уточнення до попередніх відповідей.

## З’єднання та захист витрат

Cloudflare Worker записує запит у D1. Окремий локальний контейнер
`telegram-ai-bridge` отримує його вихідним HTTPS-запитом, викликає наявні
API `availability.options`, `ai_chat.route`, `ai_chat.send`, `ai_chat.combined` та `ai_chat.question_usage` у внутрішній мережі ERP і
повертає відповідь у сталу чергу Telegram. Виклики моделі проходять через
`warehouse_core.ai.generate_text` → наявний `ai-gateway`.
OpenAI-ключ залишається тільки в наявному шлюзі; облік спільний з ERP.
Публічні порти, новий Telegram poller і тунель до ERP не потрібні.

Використано окремий обліковий запис `telegram.bot@vector-erp.invalid`
з роллю `Telegram ERP Reader`, без зміни наявних ролей інших користувачів.
Це технічний ідентифікатор, не адреса доставки листів. API-ключ ERP зберігається
лише як `ERP_API_TOKEN` у локальному `.env.ai-telegram`; у Cloudflare його немає.
Після автентифікації `telegram_access.restrict_api` дозволяє цьому обліковому
запису лише зазначені API й режими `availability`, `knowledge` та `draft`.
У режимі `draft` помічник готує текст для перегляду власником у приватному чаті. Інші REST,
RPC, v2, запис, видалення, поширення та підміна `cmd` блокуються. Це також
блокує стандартні права Desk User на зміну власного профілю чи поширення.
Авторизація токеном використовує [стандартний API Frappe](https://docs.frappe.io/framework/user/en/api/rest).

База знань додатково перевіряє доступ статті. Для читання ботом видавець
має надати статті доступ цій ролі або технічному користувачу; для відповіді
через модель стаття має бути опублікована, чинна й дозволена для ШІ.
Наявні чернетки й списки доступу не змінювалися. Відключення технічного
користувача припиняє доступ бота до ERP.

З 16 листопада 2026 року реле, ERP і шлюз витрат працюють на Contabo VPS 6.
Перевірка зв’язку відбувається раз на 15 секунд; після 45 секунд
без неї нові запити відхиляються. Шлюз використовує налаштований локальний бюджет та постійний облік витрат. `/ai залишки`, `/ai залишки: назва`
та допомога працюють без ШІ навіть при блокуванні шлюзу витрат; доступ
до ERP, власника й обмеження частоти перевіряються як раніше. Природномовні
запитання та база знань при блокуванні ШІ отримують пояснення причини й
приклад прямого пошуку. Це відповідь на запит власника, не автоматичне
повідомлення про баланс. Обмеження 95% і сповіщення лише на
75%/95% збережено. `AI_TELEGRAM_TESTS_ENABLED=false`; нові тестові
Telegram-сповіщення не надсилаються.

Запити моделі автоматично не повторюються. D1 не видає зайнятий запит вдруге;
локальна SQLite фіксує початок до виклику шлюзу й відповідь до доставки.
Після збою невизначений виклик не повторюється. Відповідь можна безпечно
повторно поставити в outbox; наявна доставка Telegram зберігає семантику
«принаймні один раз». Запит без завершення закінчується за 5 хвилин
з перевіркою щохвилини. Текст запитання видаляється при завершенні або
закінченні очікування; технічні записи D1 — через 7 днів. Локальна база
залишає лише ID завершених запитів, без текстів відповідей.

## Запуск

Міграція `services/telegram_worker/migrations/0003_ai_pilot.sql` додає
окрему таблицю. Секрет `AI_BRIDGE_TOKEN` має збігатися у Cloudflare Worker
та ігнорованому Git файлі `.env.ai-telegram`; він не є OpenAI-ключем.
Після розгортання актуального образу ERP з `telegram_access.restrict_api`
команда `python scripts/setup_telegram_erp.py` створює або перевіряє
обмежений технічний обліковий запис. Вона не друкує ключі й не змінює
наявних призначень ролей. Усі сервіси ERP повинні використовувати актуальний
образ, щоб спільний кеш Frappe не отримав старі правила доступу.

```powershell
docker compose -f compose.yaml -f compose.ai-telegram.yaml up -d --build --no-deps telegram-ai-bridge
docker compose exec -T ai-gateway python server.py status
```

Зупинка пілоту не зупиняє клієнтський бот:

```powershell
docker compose -f compose.yaml -f compose.ai-telegram.yaml stop telegram-ai-bridge
```

Для повного вимкнення приймання ШІ встановити `AI_PILOT_ENABLED=false`
у конфігурації Worker і розгорнути його. Правила підтвердження балансу й
приймання нового сервера — у [контролі витрат ШІ](ai-spending-control.uk.md).

### Розмовний формат відповідей

За запитом власника відповіді на природномовні запитання про залишки
починаються з короткого пояснення й описують товари, склади, фізичну та
вільну кількість реченнями. Ненульові резерви, потреби й очікувані поставки
пояснюються окремо. Фільтри та час перевірки перенесено в кінець.
Нульові залишки, повний резерв, порожні та часткові результати мають
окремі формулювання. Різні товари, компанії й одиниці не підсумовуються.

Текст складається локально з дозволених ERP-даних: додаткового запиту до
моделі чи передачі їй складських рядків немає. Прямі команди й кнопки
«без ШІ» зберігають компактний формат. Це зміна подачі, а не додавання
історії розмови або нових прав. Пройшли 17 тестів релею, перевірено
форматування живого результату ERP без виклику моделі, встановлені застосунки
та 8 транзакційних перевірок із відкотом. Telegram-тестів не надсилали.
