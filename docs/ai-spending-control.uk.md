# Контроль витрат на ШІ у Вектор ERP

Команда **/usage** читає локальний бюджет і резерви та показує суму, доступну до зупинки на 95%. Шлюз зберігає дозволені заголовки лімітів запитів і токенів зі звичайних відповідей OpenAI, зокрема з HTTP-помилок. Час у звіті вказує, коли API повернув ці значення. Якщо заголовків ще немає, команда повідомить про це. [Заголовки лімітів OpenAI](https://developers.openai.com/api/docs/guides/rate-limits).

З 5 листопада 2026 року шлюз обчислює пороги за локальним бюджетом і накопиченими витратами Вектор ERP. Для поточного бюджету $7 сповіщення 75% відповідає $5.25, а захисна межа 95% — $6.65. Шлюз не вимагає перевірки фінансування API, підтвердження балансу чи подовження строку гранту. Облік охоплює лише запити через цей шлюз.

## Як працює обмеження

Єдиний шлях для майбутніх функцій ШІ: `warehouse_core.ai.generate_text` →
внутрішній `ai-gateway` → OpenAI. Ключ із `.env.local` отримує лише шлюз;
контейнери ERP його не отримують. Шлюз не має опублікованого порту.
Нові функції повинні перевіряти права на бізнес-документи перед викликом цього
методу. Метод навмисно не відкрито як загальнодоступний API браузера.

Приватний [Telegram-пілот](telegram-ai-pilot.uk.md) використовує той самий
`ai-gateway` через окремий вихідний релей та дозволені API ERP. Дозволено лише
числовий ID власника у приватному чаті. Залишки не передаються моделі;
база знань передає лише дозволені чинні статті. Нового OpenAI-ключа,
окремого бюджету або паралельного обліку витрат немає.

Перед кожним запитом шлюз атомарно резервує його найбільшу дозволену вартість.
Якщо витрати разом із резервами перевищили б 95% локального бюджету,
запит не надсилається. Паралельні виклики використовують спільну базу SQLite
у постійному томі `vector-erp_ai-ledger`. Облік не скидається після перезапуску.

Після відповіді резерв замінюється розрахунком за кількістю вхідних, вихідних,
кешованих і записаних у кеш токенів. Якщо деталізації кешу немає, застосовується
верхня оцінка. При помилці, тайм-ауті або невідомому результаті весь резерв
залишається, а ШІ вимикається до перевірки. Автоматичних повторних запитів немає.

Зараз дозволено лише текстові запити до `gpt-6-luna`, стандартну обробку,
кеш на 30 хвилин і до 2048 вихідних токенів. Інструменти, файли, пошук,
зображення та вибір іншої моделі не підтримуються. Максимальний резерв одного
запиту — $0.264036. Через цей запас шлюз може зупинити запити трохи раніше
95%. Знижки не потрібні для гарантії ліміту.

Тарифи звірено з [описом моделі](https://developers.openai.com/api/docs/models/gpt-6-luna)
та [правилами кешування](https://developers.openai.com/api/docs/guides/prompt-caching).
Тарифи повторно звірено 16 листопада 2026. З 20 листопада 2026, 00:00 UTC потрібна наступна перевірка тарифів і
оновлення `PRICE_VALID_UNTIL`; до цього нові запити блокуються. Просте
подовження дати без перевірки цін неприпустиме.

## Налаштування бюджету

Для наявного пілоту використовується збережена сума та той самий період. Після перезапуску облік продовжується автоматично. Для нового встановлення задайте операторський бюджет у мільярдних частинах USD ($1 = 1000000000) та сталий ідентифікатор періоду. Далі ввімкніть шлюз.

```powershell
'{"period":"pilot","allowance":7000000000}' | docker compose exec -T ai-gateway python server.py budget --file -
docker compose exec -T ai-gateway python server.py enable
docker compose exec -T ai-gateway python server.py status
```

Для зміни суми наявного бюджету використовуйте його поточний `period` зі статусу. Зміна суми зберігає накопичені витрати й резерви. Новий період можна почати лише після вимкнення шлюзу та звірки всіх резервів. Старі файли `snapshot` підтримуються для переносу раніше врахованих витрат.

Невизначені результати потребують звірки з OpenAI перед відновленням.
Для нових викликів шлюз передає ID резерву як `X-Client-Request-Id`. У разі помилки в таблиці `request_incidents` зберігаються тип помилки та, за наявності відповіді HTTP, статус і `x-request-id` провайдера. Текст запитання й відповіді до цього запису не входять. Для звірки використовуйте час UTC, ключ проєкту та хвилинний експорт з [OpenAI Analytics](https://platform.openai.com/settings/organization/analytics/usage). Порожній інтервал у свіжому експорті не підтверджує нульову вартість.
Не видаляти базу або том для зняття блокування. Перед переносом сервісу
вимкнути ШІ, завершити/звірити запити та зберегти том обліку разом із резервною
копією ERP; звичайний `bench backup` цей окремий том не охоплює.

## Сповіщення та перевірки

### Обов'язкове приймання розгортання ERP

Вимога власника від 1 листопада 2026 року: після розгортання Вектор ERP
сповіщення також мають працювати. Розгортання не вважається завершеним,
доки не перевірено такі умови:

- Шлюз витрат і процес доставки Telegram працюють на цільовому сервері
  незалежно від комп'ютера власника; саме розгортання сайту на Pages цього не забезпечує.
- Секрети OpenAI й Telegram передано безпечно; перевірено приватного одержувача
  `@notuxius` і бота `@mtech_customer_support_bot`. Email-сповіщення не вмикаються.
- Перенесено облік витрат, резерви, події та чергу доставки без обнулення.
  Перед переносом зупинено старий шлюз після завершення або звірки запитів;
  два незалежні шлюзи з одним бюджетом одночасно не запускаються.
- Перевірено автоматичний запуск сервісу після перезапуску хоста та збереження
  обліку/черги; резервна копія охоплює окремий том шлюзу.
- Пройшли перевірки порогів 75%, 95%, паралельних запитів і незалежного
  95-відсоткового блокування. Збій Telegram не дозволяє перевищувати ліміт.
- Із цільового сервера надіслано явно позначений тест з унікальним ID цього
  розгортання; перевірено підтвердження Telegram, відсутність помилки й повтору
  того самого тесту. За уточненням власника від 04.11.2026 цей тест дозволений
  лише за його прямим запитом для першого приймання нового сервера. Звичайні
  оновлення, локальні перевірки й перезапуски використовують наявне підтвердження
  та автономні тести, без нових повідомлень. Лише локальний тест або
  `configured=true` не підтверджує доставку нового сервера.
- Перед увімкненням ШІ налаштовано локальний бюджет, перевірено тарифи та стан незавершених запитів.

Результати приймання й ID тестового повідомлення зберігаються в записі про
розгортання.

16 листопада 2026 року на Contabo VPS 6 перенесено чинний бюджет $7, усі 78
запитів і 12 попередніх підтверджень доставки. На момент переносу витрати
становили $0.007649405, відкритих резервів не було. Попередній шлюз вимкнено.
На VPS пройшли 47 автономних перевірок. Після перезавантаження сервера шлюз
відновив облік і чергу; резервна копія містить базу ERP, файли та окрему
базу обліку ШІ. Telegram підтвердив ідентичність бота й приватного чату
власника. На прямий запит власника VPS надіслав один тест
`contabo-vps6-20261116-first-deployment`: підтвердження Telegram `1062`,
одна спроба, без помилки. Для постійного процесу тестування вимкнено.

### Поточна доставка

1 листопада 2026 року на прохання власника видалено 15-хвилинний монітор
Codex. Замість нього сам шлюз надсилає **лише Telegram-сповіщення** про
75% та 95% у приватний чат `@notuxius` через
`@mtech_customer_support_bot`. Email-сповіщення про використання ШІ не
налаштовуються за останньою вказівкою власника. Окремий монітор відповіді
підтримки OpenAI також видалено після першої змістовної відповіді.

Шлюз зберігає суму та ліміт на момент події й чергу доставки в тому самому
постійному томі. Фоновий процес без викликів ШІ обробляє чергу кожні 5 секунд;
без нових подій запити до Telegram не виконуються. Перед відправленням
перевіряються бот і приватний одержувач. Інші чати, групи та клієнти бота
не отримують ці повідомлення. Webhook і сценарії клієнтського бота не змінено.

Один поріг створює одне повідомлення за кредитний період. Повторна перевірка
або звичайний перезапуск не дублює успішно доставлені повідомлення. Невдала
доставка повторюється з паузою, зокрема з урахуванням Telegram `retry_after`.
Збій між прийняттям повідомлення Telegram і записом підтвердження може
спричинити дублікат — абсолютна гарантія одноразової доставки неможлива.
Зміна одержувача не перенаправляє стару чергу іншій людині.

Поріг 95% також повідомляє про ранню захисну зупинку, якщо наступний запит
із резервом не вміщується в ліміт. У тексті вказуються поточна оцінка та
причина: резерви не оголошуються фактично витраченими коштами. Локальний
облік чітко відрізняється від рахунку OpenAI. Помилка Telegram не знімає
95-відсоткове обмеження й не впливає на облік запитів.

Доставка працює, доки запущено локальний сервіс ERP/шлюзу та доступний інтернет;
після запуску збережена черга продовжується. Зупинений комп'ютер не надсилає
повідомлення. Поточні витрати й резерви зберігаються у постійному томі.

## Історія перевірок 4 листопада 2026 року

За вказівкою власника від 04.11.2026 автоматичні Telegram-сповіщення про ШІ
обмежено порогами 75% і 95%. Застаріле підтвердження балансу, закінчення
строку/безпечної межі, необхідність перевірки тарифів і невизначений результат
запиту більше не створюють повідомлень. Раніше поставлені в чергу операційні
повідомлення позначаються `suppressed`; історія доставлених зберігається.
Інші захисні блокування та резерви залишаються чинними; щогодинне блокування
балансу пізніше скасовано власником. Причини видно у стані
шлюзу. Тестові відправлення за замовчуванням вимкнено.

Зміну застосовано до локального `ai-gateway` 04.11.2026 о 11:19 за Києвом.
Пройшли 43 автономні тести та 8 транзакційних перевірок ERP з відкочуванням
тестових записів; встановлені застосунки перевірено. Контрольна сума модуля
сповіщень у контейнері збігається з вихідним файлом, `/health` повертає `ok`.
Перед оновленням збережено `/data/pre-threshold-only-20261104T091847Z.sqlite3`.
Витрати $0.0000852, нуль резервів та історію 7 доставлених повідомлень
збережено; черга порожня, помилок доставки немає. Нове тестове повідомлення
не надсилали відповідно до прохання власника отримувати лише порогові
сповіщення. Це локальна зміна політики повідомлень, не приймання нового
серверного розгортання.

Стан доставки показується в `notifications` команди `server.py status`.
За проханням власника від 04.11.2026 `AI_TELEGRAM_TESTS_ENABLED=false`:
команда `test-notifications` відхиляється, а невідправлені тестові повідомлення
позначаються `suppressed` перед доставкою. Історія й підтвердження доставки
зберігаються. Новий ID більше не обходить цю заборону. Пороги 75% і 95% та
незалежний захисний ліміт 95% залишаються чинними.

Причина зміни: 04.11.2026 локальні перевірки створили 10 тестів із різними ID;
кожен був доставлений один раз. Звичайні перевірки мають використовувати
підставний Telegram API. Увімкнення справжнього тесту допускається лише після
прямого запиту власника; новий сервер без такого підтвердження не вважається
повністю прийнятим. Ключ бота читається з виключеного з Git `.env.telegram`; секрети не
зберігаються в образі чи повідомленнях. Документація доставки:
[Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

Заборону тестових відправлень застосовано до локального шлюзу 04.11.2026
о 12:07 за Києвом. Перевірено живий `/status`: `tests_enabled=false`,
черга порожня, 12 попередніх доставок збережено, останнє підтвердження `798`.
Нових повідомлень не надсилали. Облік $0.0003544 та нуль резервів збережено;
`/health` — `ok`, контрольна сума модуля збігається з вихідним файлом.
Пройшли 45 автономних тестів і 8 транзакційних перевірок ERP з відкотом
тестових записів; встановлені застосунки перевірено. Резервна копія обліку:
`/data/pre-disable-delivery-tests-20261104T100711Z.sqlite3`.

Тести не використовують платні API-виклики:

```powershell
python -m unittest discover -s services/ai_gateway -v
```

Покрито точну межу 95%, паралельні резерви, перезапуск, невизначену відповідь,
зміни коштів, роботу без щогодинного оновлення балансу, строк гранту/тарифів, правильний облік кешу й токенів,
дедуплікацію подій та відсутність виклику провайдера при блокуванні. Окремі
тести доставки перевіряють обидва чинні пороги, придушення скасованих порогів,
приватного одержувача, чергу
після перезапуску, паралельних відправників, повтори після помилок і відсутність
зміни витрат під час тестового повідомлення.

### Скасування щогодинного підтвердження 04.11.2026

За прямим запитом власника прибрано `credit_snapshot_stale` як умову
блокування запитів. Оновлено й перезапущено шлюз та релей, у Telegram прибрано
вимогу повторного підтвердження балансу (Worker
`352b5f16-dd69-4c9d-99d9-938d704a1af5`).
Живий `/status` після розгортання: `can_request=true`, `block_reason=null`,
`balance_refresh_required=false`, вік фактичного знімка 4476 секунд.
Час спостереження залишився `1793807846`; його не підміняли. Облік
$0.0005009, резерви $0, межа $6.65 та строк коштів збережені.
`snapshot_valid_until` тепер відображає строк коштів, а
`snapshot_age_seconds` — давність спостереження без погодинного блокування.

Пройшли 47 тестів шлюзу й сповіщень, 13 тестів релею, 27 тестів Worker
та 8 транзакційних перевірок ERP з відкотом. Встановлені застосунки перевірено.
Telegram-тестів і платних запитів під час перевірки не виконували:
`tests_enabled=false`, доставок 12, receipt `798`, черга порожня.
Резервна копія перед зміною:
`/data/pre-remove-hourly-balance-check-20261104T171021Z.sqlite3`.

### Оновлення локального розгортання 5 листопада 2026 року

У Docker Desktop оновлено Вектор ERP, шлюз витрат і релей Telegram.
Міграція сайту `frontend` і вісім транзакційних перевірок пройшли успішно.
Копії сайту та обліку витрат перед оновленням збережено в
`backups/20261105-162459/`.

Після перезапуску шлюз відкрив наявний том `vector-erp_ai-ledger`.
За локального бюджету $7 межа блокування становила $6.65.
Шлюз підтвердив пороги 75% і 95%, нуль повідомлень у черзі та 12 доставлених.
Для цього хоста повторно перевірено наявну квитанцію Telegram `798`.
Тестові повідомлення вимкнено. Шлюз і релей працюють на комп’ютері власника.
