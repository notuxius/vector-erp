# Наявність товарів і деталей у Вектор ERP

Мета першого етапу — допомогти підготувати деталі до складання верстатів ЧПК:
бачити фактичні залишки, фізичні резерви та вже зареєстровану виробничу потребу.
Джерело — встановлена ERP, включно з наявними навчальними записами. Тимчасовий
сайт https://mtech-design-preview.pages.dev/ не є офіційним довідником або
джерелом залишків. Його товари, назви й рекламні твердження не імпортуються.

## Як користуватися

Відкрийте **Векторія ✦ ШІ-помічник → Залишки та база знань**. Запитайте
«Які товари є в наявності?» або «Покажи деталі з виробничою потребою».
Ці запитання повертають лише складські дані. Якщо додати запитання про характеристики товару, помічник окремо покаже відповідь із бази знань.
Для точного пошуку розгорніть **Фільтри залишків**: назва/артикул, компанія,
склад, точна група товарів та вид залишків. Натисніть **Показати залишки**.
Панель згорнеться. Щоб змінити вибрані умови, знову відкрийте **Фільтри залишків**.
Пошук за назвою знаходить буквальну частину назви або артикула, без підстановок.
Група не включає дочірні групи автоматично.

Картка показує товар і посилання на його запис, компанію, склад, одиницю обліку,
фізичний залишок, фізичний резерв і вільну від фізичних резервів кількість.
Розгорніть **Потреби та очікувані закупівлі**, щоб побачити окремі показники
виробничих замовлень, виробничих планів, продажів, субпідряду й закупівель.
Час перевірки та часовий пояс наведено над результатом.

**Показати ще** завантажує наступні 20 пар товар–склад. **Оновити ці залишки**
повторює відповідний пошук. Кожен запит читає ERP заново. Між сторінками залишки
можуть змінюватися; це не зафіксований звіт на історичну дату. Для великих
вибірок звузьте пошук: до 500 записів області/пошуку товарів і до 2000 перевірених
складських записів за один запит. Часткова вибірка явно просить уточнення.

## Значення кількостей

| Показник | Джерело ERP | Значення |
|---|---|---|
| Фізично | `Bin.actual_qty` | Поточна облікова кількість на конкретному складі |
| Фізичний резерв | `Bin.reserved_stock` | Кількість із механізму Stock Reservation Entry |
| Вільно від резервів | `max(0, actual_qty - max(0, reserved_stock))` | Фізичний залишок без фізичних резервів |
| Виробничі замовлення | `reserved_qty_for_production` | Невикористана/непередана потреба відкритих виробничих замовлень за логікою ERPNext |
| Виробничі плани | `reserved_qty_for_production_plan` | Потреба, яку ERPNext обліковує для виробничих планів |
| Продажі / субпідряд | `reserved_qty` / `reserved_qty_for_sub_contract` | Відповідні планові потреби |
| Очікувані закупівлі | `ordered_qty` | Замовлено, але ще не отримано |

Планову потребу не віднімаємо повторно від фізичного резерву: ці значення
можуть перетинатися. Вільний фізичний залишок не означає, що його можна
безумовно використати для нового верстата: перевірте призначення, серії,
партії, стан якості та вимоги BOM. Транзитні, браковані, вимкнені й групові
склади виключено. Вимкнені товари, послуги та шаблони варіантів не показуються.
Відсутній чи прихований складський запис не перетворюється на нуль.

## Доступ, контекст і ШІ

Доступні лише автентифіковані System User з правами читання потрібних полів
Company, Warehouse, Item і Bin. Запити застосовують User Permissions,
обмеження списків та перевірку конкретних документів. Компанії, склади,
товари й поля перевіряються при кожному пошуку, включно з наступною сторінкою
та уточненням. Фільтри не дають додаткових прав; підказки містять лише дозволені
значення. Ролі користувачів не змінюються.

У Redis на 30 хвилин зберігаються тільки фільтри та позиція наступної сторінки,
прив'язані до користувача, сеансу та режиму. Залишки й попередні відповіді
не зберігаються в цьому контексті та не надсилаються до OpenAI. Модель отримує
текст запиту й попередні фільтри та повертає обмежений JSON. Сервер перевіряє
ключі, типи, довжини, дозволені види пошуку й доступ. Довільний SQL, зміни
документів, ціни, розрахунок комплектності BOM та зовнішні сайти не виконуються.

Типові загальні запити, оновлення, наступна сторінка й форма фільтрів не
викликають модель. Інші формулювання мають максимум один виклик через
`warehouse_core.ai.generate_text`, до 512 вихідних токенів, без автоматичних
повторів. Текстовий шлюз не розширюється довільними інструментами. При його
блокуванні залишається локальний пошук за фільтрами. Ліміт шести запитів за
хвилину та один одночасний запит на користувача застосовуються до чату.

Шлюз застосовує локальний бюджет, перевірку тарифів, сповіщення на 75% та 95% і незалежну зупинку на 95%.
Див. [приймання розгортання](ai-spending-control.uk.md).

## Перевірки

```powershell
docker compose exec -T backend bench --site frontend execute warehouse_core.verify_availability.run
docker compose exec -T backend bench --site frontend execute warehouse_core.verify_ai_chat.run
python scripts/check_ai_chat.py
python -m unittest discover -s services/ai_gateway -v
```

Транзакційна перевірка працює лише на явно налаштованому демосайті. Створює
тимчасові товари, надходження, продаж і фізичний резерв, BOM та виробниче
замовлення, перевіряє списання деталей після виготовлення й скасування резерву.
Також перевіряє пагінацію, реальні User Permissions, поля, document hooks,
гостей та незмінність призначених ролей. Усі тестові бізнес-записи відкочуються.
Автоматичні тести використовують підставний провайдер і не витрачають коштів.

### Локальне приймання 04.11.2026

Оновлено локальний образ `vector-erp` та сервіси ERP. Контрольні суми
серверного модуля, чату, перевірок, JavaScript і CSS збігаються з робочими
файлами. Встановлено Frappe 16.51.0, ERPNext 16.50.0, Warehouse Core 0.1.0.
Пройшли 9 перевірок меж доступу/планувальника, 6 груп транзакційних перевірок
наявності, 17 перевірок чату, 17 HTTP-перевірок, 43 тести шлюзу/сповіщень
і 8 загальних транзакційних перевірок ERP. Тестові записи відкочено,
призначення ролей збережено.

У браузері перевірено початковий запит про наявність, природний запит
«Покажи вільні шпинделі», пошук за складом і виробничою потребою та
відображення на ширині 390 px. Два навмисні виклики перевірили розпізнавання
українських форм назв; після виправлення запит зі словом «шпинделі» знаходить
наявні навчальні шпиндельні вузли та картридж. Оцінка витрат шлюзу зросла
з $0.0002709 до $0.0003544, незавершених резервів немає; це локальний облік,
а не остаточний рахунок провайдера.

Пороги 75/95% та незалежний cutoff 95% підтверджено. Навмисний тест
`local-availability-20261104` доставлено до приватного Telegram-чату власника,
receipt `798`, черга порожня. Шлюз і доставка залишаються локальним пілотом;
автономне серверне розгортання цим не приймається.

Наступний етап для прискорення виробництва: затверджені BOM, комплектність
конкретного верстата, дефіцити з урахуванням призначення резервів та строки
закупівель/виготовлення деталей. Це окрема функція, а не висновок із загального
залишку. Поточний етап нічого не резервує й не створює автоматично.
